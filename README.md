# keeper2

占住的卡，在你**不跑作业的时候也不留空隙**；你自己的进程一出现，占位进程立刻让路；别人的进程进不来。

为 “agent 做优化” 这类用法写的：agent 改代码、想方案的那几分钟里卡上没有测试在跑，v1 留出来的显存是空的，别人的作业（或者别人的自动抢卡脚本）就落进来了，下一次测试要么 OOM，要么计时被干扰。

单文件 Python（只用标准库 + NVIDIA 驱动自带的 `libcuda` / `libnvidia-ml`），不需要 torch，不需要改实验代码。

## 和 v1 的区别

| | v1 `gpu_keeper.sh` | keeper2 |
|---|---|---|
| 没有作业时 | 留 `RESERVE_GB` 空着，谁都能申请 | 整张卡占满，只留约 250 MiB |
| 自己的作业要显存 | 用留出来的那部分 | 占位进程实时让出，作业结束立刻补回 |
| 别人的进程 | 能落进空着的部分 | 连 CUDA 上下文都建不起来，启动即失败 |
| 卡被别人进了 | 自己发现、自己处理 | 标记出来，自动补占一张备用卡，对方走后归还 |
| 占位进程依赖 | 带 torch 的镜像 | 任何带 python3 的镜像，或者不用 docker |
| 选卡、设环境变量 | 读 `held` 文件自己写 | `keeper2.py run -- 命令` |

v1 的三个脚本原样保留，仍然可用。不要让 v1 和 keeper2 的占位进程待在同一张卡上：v1 的占位进程是你的 uid，keeper2 会把它当成你的作业而一直让路。

## 原理

每张被占的卡上有一个占位进程（holder），每 10 ms 看一次这张卡：

```
            你的进程出现                         你的进程全部结束
 ┌────────┐ ───────────────────────▶ ┌────────┐ ─────────────────▶ ┌────────┐
 │ sealed │                          │  open  │                    │ sealed │
 │ 占满   │ ◀─────────────────────── │ 全让出 │                    │ 占满   │
 └────────┘      约 10–40 ms 补满     └────────┘                    └────────┘
     │  keeper2.py run -m 12 -- cmd      │ 设了 --headroom 且作业稳定后
     ▼                                   ▼
 ┌────────┐                          ┌──────────┐
 │ leased │ 只让出 12 GiB，其余照占   │ tracking │ 只在你的用量之上留 H GiB，随用量移动
 └────────┘ 命令结束即收回            └──────────┘
```

- **sealed（封住）**：占到只剩一条 “落脚缝”（默认是一个 CUDA 上下文大小的一半，最多 256 MiB）。一个 CUDA 进程光建上下文就要约 0.5 GiB，所以别人的进程在 `cuCtxCreate` 这一步就 out of memory，根本起不来。
- **open（让路）**：你的进程开始建上下文时先占十几 MiB，约 60 ms 后出现在驱动的进程列表里，这时它的上下文还要 100 多毫秒才能建完。占位进程在这段时间里认出它是你的，把显存全部放掉。所以 **你的作业不用改任何命令**，哪怕第一笔申请就是 28 GiB 也能成功。
- **怎么算 “你的”**：进程的 uid 是你；或者进程所在的 docker 容器被你声明过（`--own-mounts` / `--own-containers`，见下）。其余一律算别人的，包括看不到属主的进程，以及驱动列不出来、但确实占着显存的部分。
- **对别人的占用绝不后退**：占位进程只在 “你的作业有权使用的空间” 变大时才缩小。别人占掉的显存不会让它再吐出更多。
- 占位进程只占显存，不占算力，不发任何 GPU 计算；也从不动别人的进程。

keeper（后台守护进程）负责：等空闲卡出现并占上、占位进程挂了就重启、卡被别人进了就补占备用卡。

## 快速开始

```bash
git clone https://github.com/LiHaoxu/gpu-keeper && cd gpu-keeper/keeper2

./keeper2.py up -n 2          # 占 2 张卡。没有空闲卡就一直等；一张卡空闲满 30 s 才会被占
./keeper2.py status           # 占了哪些卡、谁在卡上、挡掉了几次
./keeper2.py down             # 用完后全部释放
```

`status` 的样子：

```
keeper2 2.0.0   keeper: running   target 2 (+1 spare)   docker mode   state /dev/shm/gpu-keeper2-lihaoxu
GPU  STATE     RESERVED    YOURS   OTHERS     FREE  NOTES
0    -                -        -     6.3G    25.1G  alice 6.3G
1    -                -        -        -    31.4G
4    sealed       30.6G        -        -     259M  blocked 2
5    leased       22.6G     7.5G        -     780M  lease 8.0G 0:04 (docker run --gpus device={gpu} --rm …); leased pid 1527381 7.5G python3 bench.py
```

4 号卡封着，挡掉过 2 次别人的进程；5 号卡上有一个 `run -m 8` 的作业，用了 7.5 GiB，其余 22.6 GiB 仍被占着；0 号卡没占，上面是别人的作业。

跑实验有三种方式，可以混用：

**1. 什么都不改（进程 uid 是你自己）**

裸机上直接跑的程序，或者 `docker run -u $(id -u):$(id -g) …` 起的容器，占位进程会自动让路：

```bash
docker run --rm --gpus device=4 -u $(id -u):$(id -g) … python train.py
```

**2. docker 里以 root 跑的作业：声明哪些容器是你的**

root 容器里的进程在宿主机上都是 uid 0，和别人的分不出来。告诉 keeper2 怎么认：

```bash
./keeper2.py up -n 2 --own-mounts /data/lihaoxu        # 挂载了这个目录（或其子目录）的容器算我的
./keeper2.py up -n 2 --own-containers '^(lhx-|photonzip$)'   # 或者按容器名的正则
```

这两个参数可以在 keeper 运行期间随时改（再执行一次 `up` 即可），对 `docker exec` 进长期容器里跑的进程同样有效。

**3. `run`：显式申请（最确定，对任何命令都有效）**

```bash
./keeper2.py run -- python bench.py                                   # 自动挑一张占住的卡
./keeper2.py run -m 12 -- docker run --rm --gpus device={gpu} img …   # 只要 12 GiB，其余继续封着
./keeper2.py run -n 2 -- torchrun …                                   # 两张卡
./keeper2.py run -x -- ./timing_benchmark                             # 独占：计时期间这张卡上没有你的其他 run
```

多卡时 `{gpu}` 是 `4,5` 这样的列表，docker 的写法要多一层引号：`--gpus '"device={gpu}"'`。

`run` 做的事：挑卡 → 让占位进程腾出显存并等它确认 → 设好 `CUDA_VISIBLE_DEVICES`（以及 `CUDA_DEVICE_ORDER=PCI_BUS_ID`、`KEEPER2_GPU`）→ 把参数里的 `{gpu}` 换成卡号 → **exec** 成你的命令。没有包装进程：退出码、信号、终端都是命令自己的；命令一结束（包括被 `kill -9`），显存在约 10 ms 内被收回。

## 给 agent 用

让 agent 自己跑测试时，把下面这段放进项目的 `CLAUDE.md`（或你给 agent 的说明）里：

```markdown
## GPU
这台机器的 GPU 是共享的，我们的卡由 keeper2 占着（`/path/to/keeper2.py status` 查看）。
- 所有要用 GPU 的命令都通过 `/path/to/keeper2.py run -- <命令>` 启动；docker 命令里用 `--gpus device={gpu}`。
- 不要自己选卡，不要设置 CUDA_VISIBLE_DEVICES，不要在没被占住的卡上跑。
- 计时类的测试加 `-x`；知道显存用量时加 `-m <GiB>`。
- 报 “no GPU is held” 时不要绕过去：先用 `status` 看情况，或者加 `--wait` 等卡。
- 不要执行 `keeper2.py down`，除非我明确说释放。
```

这样两次测试之间卡是封住的，测试启动时自动拿到显存，agent 不需要知道卡号。

## 命令

| 命令 | 作用 |
|---|---|
| `up [选项]` | 启动 keeper；keeper 已在运行时则是修改设置（目标数量、候选卡、headroom 等立即生效） |
| `down` | 停止 keeper 和所有占位进程，释放全部的卡。正在跑的作业不受影响 |
| `status [--json]` | keeper 状态、每张卡的状态、租约、卡上的进程 |
| `run [选项] -- 命令…` | 在占住的卡上运行命令（见上） |
| `lease [-g 卡] [-m GiB] [--ttl 秒]` | 定时租约：在一段时间内腾出显存。给没法用 `run` 启动的作业用，例如 `docker run -d` |
| `release <id>… \| --all` | 提前结束租约 |
| `gpus [-a]` | 打印可用的占住的卡号（逗号分隔），给脚本用；`-a` 包含被别人进了的卡 |
| `log [-n 行数]` | keeper 和各占位进程的事件日志（毫秒时间戳）：谁来过、挡掉了谁、每次让出和收回 |

`run` 的选项：

| 选项 | 含义 |
|---|---|
| `-m GiB` | 命令需要的显存，如 `12`、`500m`；默认整张卡。越贴近实际用量，测试期间卡封得越严 |
| `-g 卡号` / `-n 数量` | 指定卡，或者要几张卡（默认 1 张，挑租约最少的） |
| `-x` | 独占：等这张卡上其他 `run` 结束，运行期间也不让别的 `run` 进来 |
| `-w [秒]` | 没有占住的卡时等待而不是报错（不带数值：一直等） |

`up` 的主要选项：

| 选项 | 默认 | 含义 |
|---|---|---|
| `-n N` | 1 | 要保持多少张**可用**的卡 |
| `-c 0,2,4-7` | 全部 | 只在这些卡里挑 |
| `--headroom GiB` | off | 见 “收得更紧” |
| `--own-mounts 路径,…` | 无 | 挂载了这些目录的容器算你的 |
| `--own-containers 正则` | 无 | 名字匹配的容器算你的 |
| `--spare K` | 1 | 占住的卡被别人进了时，最多额外补占几张 |
| `--idle-secs S` | 30 | 一张卡连续空闲这么久才去占，避免抢在别人两次作业的间隙里 |
| `--idle-mib M` | 100 | 显存占用低于它且没有计算进程才算空闲 |
| `--idle-util P` | 100 | 利用率高于 P% 的卡不算空闲（100 = 不看利用率；同等条件下总是先占利用率低的） |
| `--landing-mib M` | 自动 | 封住时留的落脚缝。默认取上下文大小的一半，最多 256 |
| `--intruder-mib` / `--intruder-secs` | 100 / 20 | 别人的显存超过这么多、持续这么久，这张卡记为 INTRUDED |
| `--mode docker\|host` | 自动 | 占位进程跑在 docker 容器里（docker 可用时的默认，同 v1），还是作为普通进程 |
| `--image IMG` | `nvcr.io/nvidia/pytorch:25.06-py3` | docker 模式下占位容器的镜像。只需要有 python3，不需要 torch；默认值沿用 v1。换镜像后先用 `tests/check_real.py --image …` 验一遍 |
| `--no-pid-host` | | docker 模式不加 `--pid=host`。占位进程看不到进程归属，只有 `run` / `lease` 能让它让路 |
| `--state DIR` | `/dev/shm/gpu-keeper2-<用户>` | 状态目录（也可以用环境变量 `KEEPER2_STATE`） |

## 收得更紧：`-m` 和 `--headroom`

默认行为把 “你的作业一定不会被占位进程卡住” 放在第一位：**你的作业在跑的时候整张卡是让出来的**。如果作业只用 8 GiB，那么测试运行期间卡上有 20 多 GiB 是真正空着的，别人这时候可以进来。两种收紧办法：

- **`run -m`**（推荐）：明确说要多少。`run -m 12` 时占位进程只让出 12 GiB（外加落脚缝），其余照占。确定、没有时序问题。每次作业结束时日志里有一行 `peak … MiB`，照着它定 `-m` 即可。
- **`up --headroom H`**（给不包 `run` 的作业）：你的进程出现时先整卡让出；等它的用量 `--settle-secs`（默认 10 s）没有再涨，占位进程就收回来，只在你的用量之上留 H GiB，之后随用量移动（10 ms 一拍）。代价：**稳定之后，单次超过 H 的申请会 OOM**，比如训练一段时间后 eval 一次性申请 6 GiB 而 H 是 4。按框架申请显存的最大单笔来定 H；一启动就按 “当前空闲显存” 预分配的框架（JAX、TensorFlow 默认行为）不要用这个模式。

同一张卡上既有 `run -m` 的租约、又有不经 `run` 启动的你的作业时，按后者处理：整卡让出（或按 `--headroom`），另外再加上租约的量。

## 卡被别人进了

窗口期（你的作业运行期间、占位进程重启期间）里别人仍可能落进来。这时：

- 占位进程不动对方，也不再让出更多显存；你的作业结束后它把剩余部分全部占上，对方的作业只能维持现有用量。
- 对方的显存持续 20 s 以上，这张卡在 `status` 里显示 `INTRUDED`，从 `gpus` 和 `run` 的自动选卡里拿掉（仍然占着，对方一走就完整拿回来）。
- 可用的卡少于目标数量时，keeper 额外补占一张空闲卡（最多 `--spare` 张）；被进的卡恢复后，多出来的那张自动归还。

`keeper2.py log` 里能看到来的是谁（用户、pid、命令行、峰值显存）。

## 实测数据

8×RTX 5090（32 GiB），驱动 595.84，占位进程跑在 docker 容器里：

| 项目 | 数值 |
|---|---|
| 封住后剩余显存 | 259 MiB（`nvidia-smi` 显示 31852 / 32607 MiB） |
| 一个空 CUDA 上下文 | 506 MiB，所以别人的进程建不了上下文 |
| 占满 31 GiB | 16 ms |
| 你的进程被认出 → 全部让出 | 45–100 ms；进程自己的上下文要 200 ms 以上才建完 |
| 你的进程结束 → 重新占满 | 10–40 ms |
| `run` 从启动到命令开始执行 | 110–170 ms，其中 Python 启动约 45 ms |
| 不改命令直接跑：PyTorch 单个 28 GiB 张量 | 成功 |
| 别人的进程（root 容器，PyTorch / 裸 CUDA） | `CUDA error: out of memory`，约 0.2 s 后退出 |
| 占位进程开销 | CPU 约 0.9% 个核，内存约 140 MB；keeper 约 0.2% 个核 |
| 占位进程被 kill → 重新封住 | docker 模式约 5 s，普通进程模式 3.6 s（keeper 先等 2 s，看它会不会自己恢复） |
| 首次占一张卡（卡空闲够久之后） | docker 模式 2–3 s，普通进程模式 0.7 s |

## 局限和注意事项

1. **不是绝对的锁。** 默认设置下，你的作业运行期间卡是开着的；占位进程被 kill 后重启的 3–5 秒里卡也是开着的。要求高就用 `-m`。docker 模式下 dockerd 偶尔会卡住（实测遇到过两次，容器创建被拖了 15–20 s），那段时间里新占的卡、重启中的占位进程都要等它。
2. **自动让路依赖驱动 “先列出进程、后建完上下文” 的时序。** 上面的数据来自一台机器。换机器先跑一遍 `tests/check_real.py`（见下），它会直接告诉你 “不改命令” 这条路在这台机器上通不通。不通的话把 `--landing-mib` 调到比一个上下文大（比如 800），或者所有作业都走 `run`。
3. **长期挂在卡上的自己的进程会让卡一直开着。** Jupyter kernel、常驻的推理服务这类进程只要还占着这张卡，默认设置下占位进程就一直让路。给它们配 `--headroom`，或者别放在占住的卡上。
4. **`run` 包的命令必须活到作业结束。** 租约跟着命令自己的进程走（exec 之后 pid 不变）：它一结束租约就结束，放到后台的子进程不算。所以 `run -- docker run -d …` 里 docker 客户端一退出，租约也就没了。这种作业用 `--own-mounts` / `--own-containers`，或者 `lease --ttl`。`-x` 的独占锁则会被后台子进程继承，要等它们也退出，别的 `-x` 才能进来。
5. **只占显存。** GPU 处于 Exclusive Process 模式的卡不会被占（占位进程和你的作业无法共存）；用 MPS 的卡上进程归属可能认不出来，走 `run`。
6. **机器重启后**：docker 模式的占位容器带 `--restart unless-stopped`，会自己回来把卡封住，这时 `run` 可用；keeper 需要你再执行一次 `up`（它会接管已有的占位容器，但设置要重新给）。普通进程模式重启后什么都不会自己回来。占位容器名是 `keeper2-<用户>-g<卡号>`，带标签 `keeper2.state=<状态目录>`，`down` 按这个标签清理。
7. **状态目录默认在 `/dev/shm`（内存里）**：状态文件写得很频繁，而且磁盘写满时不能影响作业向占位进程要显存。在容器里调用 `keeper2.py run` 时，容器要以你的 uid 运行（`-u $(id -u):$(id -g)`），要能看到宿主机的这个目录（`-v /dev/shm:/dev/shm`），并把 `KEEPER2_STATE` 设成同一个路径。这时租约靠文件锁维持，不跟进程走（容器的 pid 和宿主机的对不上）。
8. **按 uid 认人。** 别人的容器如果恰好也以你的 uid 运行（有些镜像默认就是 uid 1000），会被当成你的。
9. **用完及时 `down`。** 共享机器上长期占着不用会影响别人。

## 测试

```bash
python3 tests/test_keeper2.py          # 45 个用例，约 2.5 分钟。用模拟 GPU，任何机器都能跑（不需要显卡和 docker）
python3 tests/check_real.py --gpu 4    # 真卡自检：占用一张空闲卡约 1 分钟，跑完自动释放
```

`check_real.py` 依次检查：封住 → 你的作业不包 `run` 拿到 85% 的显存 → 结束后重新封住 → root 容器（相当于别人）被挡在外面 → 同一个容器通过 `run` 能跑 → `run -m` 的限额 → 占位进程被 kill 后恢复 → `down` 后卡是空的。它用自己的状态目录和容器名，不影响你已经在跑的 keeper（挑一张 keeper 没占的空闲卡）。

需要 Python 3.6 以上；在 3.9、3.10、3.12 上跑过。
